## 1. 背景与目标

### 1.1 业务背景
- 公司内部项目管理使用 GitLab，部署依赖 GitLab CI/CD 流程，目前以**手动触发**方式进行。
- 项目数量多，每次部署需要先到 GitLab 找到对应仓库地址、进入 Pipeline/Job 页面手动操作，**效率低、易出错**。

### 1.2 项目目标
打造一个**统一的项目部署中心**，让用户在一个界面内：
1. 按分组浏览/搜索项目，无需记忆仓库地址；
2. 选择项目 → 选择分支 → 选择环境 → **一键触发部署**；
3. 实时查看部署进度与日志；
4. 回溯部署历史，知道"谁在什么时间部署了哪个项目的哪个分支到哪个环境"。

### 1.3 衡量指标（建议）
- 单次部署操作从"找仓库到触发完成" < 30 秒。
- 部署成功率、平均部署时长在平台可观测。
- 覆盖公司 90% 以上接入 CI/CD 的项目。

## 3. 角色与权限模型

系统**不重复造权限轮子**，权限以 GitLab 为权威来源（详见 §7）。在此基础上叠加平台层角色：

| 角色 | 来源 | 能力 |
| --- | --- | --- |
| 普通用户 | GitLab 登录用户 | 浏览/搜索其在 GitLab 有 `Developer` 及以上权限的项目；对有部署权限的项目触发部署、查看自己可见项目的部署历史与日志 |
| 项目负责人 | GitLab Maintainer/Owner | 在普通用户基础上，可配置项目的环境映射、部署 Job 映射、回滚 |
| 平台管理员 | 平台内白名单（配置 GitLab 用户名/ID） | 全局配置：分组同步策略、环境定义、审计查看、Token 管理、用户黑白名单 |

**部署权限判定原则**：用户能否对某项目某环境触发部署 = 该用户在 GitLab 对应项目的角色 ≥ 配置阈值（默认 `Developer` 可部署 dev/test，`Maintainer` 可部署 prod，阈值可由平台管理员配置）。

## 4. 功能需求

### 4.1 功能模块总览

```
一键部署系统
├── 认证模块（GitLab OAuth 登录/登出/Token 刷新）
├── 项目浏览模块（分组树 + 项目列表 + 搜索 + 收藏）
├── 部署操作模块（选分支 + 选环境 + 触发 + 确认）
├── 部署监控模块（实时状态 + 进度 + 日志流）
├── 部署历史模块（历史列表 + 详情 + 筛选）
├── 多环境管理模块（环境定义 + 项目-环境-Job 映射）
└── 系统管理模块（管理员配置 + 审计 + 用户管理）
```

### 4.2 详细功能需求（FR）

#### FR-1 认证登录
- FR-1.1 用户访问系统，未登录时跳转 GitLab OAuth 授权页。
- FR-1.2 授权回调后，后端用 code 换取 access_token，建立平台会话（JWT/Session）。
- FR-1.3 展示当前登录用户头像、昵称；支持登出。
- FR-1.4 GitLab token 过期时静默刷新（refresh_token），刷新失败则要求重新登录。
- FR-1.5 平台会话有效期可配置（默认 8 小时），过期需重新登录。

#### FR-2 项目浏览
- FR-2.1 左侧展示**分组树**（多级 Group），点击分组筛选右侧项目列表。
- FR-2.2 右侧**项目列表**展示：项目名、所属分组、最近一次部署环境/状态/时间、默认分支、收藏标记。
- FR-2.3 **搜索**：按项目名/路径模糊搜索（支持拼音首字母可选增强），实时过滤；支持仅在当前分组内搜或全局搜。
- FR-2.4 **列表分页**或虚拟滚动（项目多时性能保障）。
- FR-2.5 **只展示当前用户有权限的项目**（继承 GitLab 可见范围）。
- FR-2.6 **收藏/常用项目**：用户可收藏项目，置顶展示（平台侧存储）。
- FR-2.7 列表项提供「部署」「历史」「打开 GitLab」快捷入口。

#### FR-3 部署操作（核心）
- FR-3.1 选定项目后弹出/进入部署面板。
- FR-3.2 **环境选择（主入口）**：展示该项目已配置的可部署环境（如 测试/生产），用户无权限的环境置灰。**环境与分支绑定**（见 §6.5、§FR-6），选定环境后系统自动带出对应分支。
- FR-3.3 **分支自动带出 + 可查看**：选环境后默认展示并选中该环境绑定的分支（如 测试→`develop`），分支只读展示；提供「高级/切换分支」入口供需要时手动改分支（高危操作，需权限+二次确认），可选 tag。
- FR-3.4 可选填部署变量/备注（如版本说明）。
- FR-3.5 **二次确认**：对 prod 等高危环境强制二次确认弹窗（显示项目+分支+环境）。
- FR-3.6 点击「部署」→ 后端触发 GitLab → 创建一条部署记录 → 跳转监控视图。
- FR-3.7 **并发保护**：同一项目同一环境若已有进行中部署，提示并阻止重复触发（可配置允许排队）。

#### FR-4 部署监控（实时）
- FR-4.1 展示当前部署的 Pipeline 状态：created / pending / running / success / failed / canceled。
- FR-4.2 展示**进度/阶段**：各 stage 与 job 的状态流转可视化。
- FR-4.3 **实时日志流**：拉取部署 Job 的日志并增量刷新（轮询或 SSE）。
- FR-4.4 支持**取消部署**（有权限用户）。
- FR-4.5 部署结束（成功/失败）实时反馈结果，失败展示失败 Job 链接。

#### FR-5 部署历史
- FR-5.1 历史列表字段：项目、分支、环境、触发人、触发时间、状态、耗时、Pipeline 链接。
- FR-5.2 筛选：按项目、环境、状态、时间范围、触发人筛选。
- FR-5.3 历史详情：复用监控视图，可回看当时日志（若 GitLab 仍保留）。
- FR-5.4 权限：仅可见自己有权限项目的历史；管理员可见全部。
- FR-5.5 （可选/二期）**一键重新部署**：以同样参数再次触发。

#### FR-6 多环境管理
> 说明：经真实样本确认（§8.5），现有前端项目 CI **不区分多环境**（单项目=单部署目标）。因此环境为**可选/可退化**概念——单环境项目展示一个"默认"环境即可；本模块为未来确有多环境的项目预留能力，一期不强求每个项目配多环境。
- FR-6.1 平台维护**环境字典**（默认/dev/test/staging/prod，可扩展，含排序与颜色标识）。
- FR-6.2 **项目-环境-分支-触发映射**配置（核心）：每个项目每个环境对应「绑定分支 + 如何触发」，由项目负责人/管理员配置。**分支→环境映射各项目不统一，必须做成可配置项，不可写死约定**（如 A 项目 测试=`develop`、生产=`master`；B 项目可能不同）。
- FR-6.3 支持映射的初始自动推断（默认约定 测试=`develop`、生产=`master/main`，见 §6.5）+ 手动覆盖；推断仅作初值，最终以配置为准。
- FR-6.4 环境部署权限阈值配置（哪种 GitLab 角色可部署该环境）。

#### FR-7 系统管理
- FR-7.1 分组/项目同步策略：手动刷新 + 定时同步 GitLab Group/Project 列表（缓存）。
- FR-7.2 管理员白名单配置。
- FR-7.3 审计日志查看：所有部署/取消/配置变更操作可查询。
- FR-7.4 GitLab 服务端 Token（系统级，用于同步与无人值守任务）管理。

### 5.2 为什么需要 BFF（设计依据）
1. **Token 安全**：GitLab access_token / 系统级 token 不能暴露给浏览器，必须由后端持有并代理。
2. **统一鉴权与审计**：所有部署动作在后端落库，满足"谁部署了什么"的审计要求。
3. **权限聚合**：合并 GitLab 角色 + 平台环境阈值做最终判定，前端不可信。
4. **聚合与缓存**：分组树/项目列表/分支等多次调用 GitLab，由后端缓存降低上游压力。
5. **触发抽象**：屏蔽 §8 中多种触发机制差异，前端只需一个统一"部署"接口。

## 6. GitLab API 集成方案

> GitLab REST API base：`http://10.0.6.203:8088/api/v4`
> 认证：后端在调用时附带用户 OAuth token（`Authorization: Bearer <token>`），系统级任务使用系统 token。

### 6.1 OAuth 登录流程（Authorization Code）

1. 在 GitLab 后台创建 **Application**（Admin 或用户级），获得 `client_id` / `client_secret`，配置回调地址 `https://<deploy-center>/api/auth/callback`，scope 建议：`read_api` + `api`（触发部署需要 `api`）。
2. 前端访问 `GET /api/auth/login` → 后端 302 到：
   `http://10.0.6.203:8088/oauth/authorize?client_id=...&redirect_uri=...&response_type=code&scope=api&state=...`
3. 用户授权后回调 `GET /api/auth/callback?code=...&state=...`。
4. 后端 `POST /oauth/token`（grant_type=authorization_code）换取 `access_token` + `refresh_token`。
5. 后端用 token 调 `GET /user` 拿用户信息，建立平台会话（签发 JWT，token 加密存 Redis/DB）。
6. token 过期用 `refresh_token` 刷新。

### 6.2 关键 GitLab API 清单

| 用途 | Endpoint | 说明 |
| --- | --- | --- |
| 当前用户 | `GET /user` | 获取登录用户信息 |
| 分组列表 | `GET /groups?top_level_only=true` / `GET /groups/:id/subgroups` | 构建分组树 |
| 分组下项目 | `GET /groups/:id/projects?include_subgroups=true` | 项目列表 |
| 用户可见项目 | `GET /projects?membership=true&simple=true` | 仅当前用户有权限的项目 |
| 项目详情 | `GET /projects/:id` | 含 `permissions` 字段判定角色 |
| 项目成员权限 | `GET /projects/:id/members/all/:user_id` | 取 `access_level`（10/20/30/40/50） |
| 分支列表 | `GET /projects/:id/repository/branches` | 部署选分支 |
| Tag 列表 | `GET /projects/:id/repository/tags` | 可选 |
| 创建流水线 | `POST /projects/:id/pipeline`（body: ref, variables） | 触发方案 A |
| Trigger 触发 | `POST /projects/:id/trigger/pipeline`（token, ref, variables） | 触发方案 B |
| 列出 Pipeline jobs | `GET /projects/:id/pipelines/:pipeline_id/jobs` | 找 manual deploy job |
| 播放手动 Job | `POST /projects/:id/jobs/:job_id/play`（可带 job variables） | 触发方案 C |
| Pipeline 状态 | `GET /projects/:id/pipelines/:pipeline_id` | 监控状态 |
| Job 状态 | `GET /projects/:id/jobs/:job_id` | 监控单 job |
| Job 日志 | `GET /projects/:id/jobs/:job_id/trace` | 实时日志（增量按字节 range） |
| 取消 Pipeline | `POST /projects/:id/pipelines/:pipeline_id/cancel` | 取消部署 |
| 取消 Job | `POST /projects/:id/jobs/:job_id/cancel` | 取消单 job |

`access_level` 对照：`10 Guest / 20 Reporter / 30 Developer / 40 Maintainer / 50 Owner`。

### 6.3 限流与缓存
- 后端对 GitLab 调用做**统一客户端封装**：超时、重试、错误归一化、请求合并。
- 分组树、项目列表缓存到 Redis（TTL 5~10 分钟 + 手动刷新）。
- 日志/状态轮询设置最小间隔（如 2s）避免打爆 GitLab。
- 监控 GitLab 返回的 `RateLimit-*` 头，必要时退避。

### 6.4 Webhook（可选增强，二期）
配置 GitLab Pipeline/Job Webhook → 后端接收事件实时更新部署状态，替代轮询，降低延迟与上游压力。

### 6.5 分支 → 环境 映射（已确认：按分支区分环境）

经与运维确认，**部署环境由分支区分**（如 `develop` = 测试环境），且**各项目映射不统一，需平台可配置**。设计如下：

- 数据上每个「项目 + 环境」绑定一个分支（`project_env_config.ref`，见 §9）。
- **交互模型**：用户选环境 → 系统自动带出绑定分支并触发（§FR-3.2/3.3），契合"一键部署"。
- **初始化推断（仅初值，可改）**：

  | 环境 | 默认推断分支 |
  | --- | --- |
  | 测试 | `develop` |
  | 生产 | `master` / `main` |
  | 预发（如有） | `release` / `staging` |

- 一个项目可只配置部分环境（如只有测试+生产）；未配置的环境不展示。
- 触发仍走 §8.3 方案 C：在该环境绑定的分支上创建/复用 pipeline → play 入口 `build_*` 手动 job。

## 7. 权限管理方案

### 7.1 原则
- **GitLab 为权威权限源**：用户能看到/能部署什么，以其 GitLab 角色为准，平台不维护重复的项目权限表。
- **平台层叠加**：环境部署阈值、管理员白名单、收藏等由平台维护。

### 7.2 判定流程（每次部署/查看时校验）

```
1. 平台会话校验（JWT 有效？）
2. 取用户对目标项目的 GitLab access_level（来自缓存/实时查询）
3. 可见性：access_level >= Reporter(20) → 可浏览/查看历史
4. 部署权限：access_level >= 该环境配置阈值（默认 dev/test=Developer(30)，
   staging=Developer(30)，prod=Maintainer(40)）→ 允许触发
5. 不满足 → 403，前端按钮置灰并提示
```

### 7.3 安全要点
- 所有部署相关接口**后端二次校验权限**，绝不信任前端。
- GitLab token、client_secret、系统 token 加密存储（KMS/环境变量 + 加密列），不落日志。
- 高危环境（prod）二次确认 + 审计强制记录。
- CSRF（OAuth state 校验）、XSS（日志输出转义）、接口限流。
- 全量操作审计：操作人、IP、时间、项目、环境、结果。

## 8. 部署触发方案（多机制覆盖 + 推荐）

> 你当前不确定 GitLab 现有"手动部署"的具体机制，因此系统设计为**可适配三种触发方式**，按项目映射选择；并给出推荐落地路径。

### 8.1 方案 A：创建新流水线（`POST /projects/:id/pipeline`）
- 以指定 `ref`（分支/tag）创建 pipeline，通过 `variables` 传 `DEPLOY_ENV=prod` 等控制部署目标。
- **前提**：`.gitlab-ci.yml` 中部署逻辑能根据变量/分支自动执行（部署 job 非 manual，或由 rules 控制）。
- 优点：实现简单、可携带变量、天然按用户身份触发（用用户 token）。
- 适用：CI 配置由变量驱动部署的项目。

### 8.2 方案 B：Trigger Token（`POST /projects/:id/trigger/pipeline`）
- 用项目的 trigger token 触发新流水线，携带变量。
- 优点：与具体用户解耦、稳定。
- 缺点：需为每个项目管理 trigger token；审计需平台自己记录触发人。
- 适用：希望用固定服务凭证触发的场景。

### 8.3 方案 C：播放入口手动 Job（`POST /jobs/:job_id/play`）★公司现状采用此模式
- 流程：确保目标分支有 pipeline（无则 `POST /projects/:id/pipeline?ref=<branch>` 创建）→ `GET .../jobs` 找到 **`status == 'manual'` 的入口 job** → `play` 它 → 后续 `needs` 它的 job 自动级联执行。
- **完全贴合公司现状**（见 §8.5 真实样本分析）：手动门在 `build` job 上，`deploy` job 靠 `needs` 自动跟随。
- 优点：不改动现有 `.gitlab-ci.yml` 即可接入。
- 缺点：需先有/创建 pipeline；需可靠识别"入口手动 job"。
- **识别入口手动 job 的策略（按可靠性排序）**：
  1. 取 pipeline 全部 job，筛 `status == 'manual'`；
  2. 若多个，取 `stage` 最靠前的（如 `build`）；
  3. 命名兜底：匹配 `build_*`（公司约定），再不行匹配 `deploy_*`。
  - **不要写死 `deploy_<env>`**，因为真正的手动门在 `build_*` 上。

### 8.4 统一抽象与推荐落地

后端定义部署策略接口，按"项目-环境"映射选择 A/B/C：

```ts
interface DeployStrategy {
  trigger(ctx: { projectId; ref; env; userToken; variables }): Promise<{ pipelineId; jobId? }>
}
// 映射示例
{
  projectId: 123,
  env: 'prod',
  strategy: 'manual_job',     // playJob | createPipeline | triggerToken
  jobNamePattern: 'deploy_prod'
}
```

**约定优于配置（自动推断，基于真实样本）**：默认走方案 C —— 创建/复用目标分支 pipeline → 识别入口 `status==manual` 的 job（优先 `build_*`，stage 最靠前）→ play → 监控级联的 `deploy_*` 直到终态。识别不到手动 job 时回退方案 A。项目负责人可在 §FR-6.2 手动覆盖（指定 job 名或策略）。

**推荐路线**：
1. **一期**：方案 C 为主，按"入口手动 job"规则覆盖现有前端项目（已验证符合样本）；
2. 对无手动 job 的项目用方案 A 兜底；
3. **二期**：支持方案 B 与每项目自定义映射，接 Webhook 优化实时性。

### 8.5 真实样本分析（web-saas-operation，已确认）

基于你提供的 `.gitlab-ci.yml`，公司前端项目的部署模式如下：

```yaml
stages: [build, deploy]
build_<service>:   # stage=build, when: manual  ← 唯一手动门
deploy_<service>:  # stage=deploy, needs: build_<service>  ← 自动级联，无手动门
# 部署目标 SERVER_HOST 写死，无 DEPLOY_ENV 变量，单项目=单环境
```

由此固化的平台规则：

| 维度 | 规则 |
| --- | --- |
| 触发动作 | play `stage==build` 且 `status==manual` 的 job（命名 `build_*`） |
| 部署完成判定 | 级联的 `deploy_*` job 进入 `success`（或 pipeline 终态） |
| 无 pipeline 时 | 先 `POST /pipeline?ref=<branch>` 创建，再找手动 job play |
| 监控范围 | 从 build 手动 job 起，跟踪 build→deploy 整条链路日志与状态 |
| 日志展示 | 同时支持看 `build_*` 与 `deploy_*` 两个 job 的 trace |
| 环境概念 | **按分支区分环境**（已与运维确认）：如 `develop`=测试、`master`=生产。映射各项目不同，平台做成可配置（见 §6.5、§FR-6.2） |

> ✅ 已确认：环境由分支区分（`develop`=测试），映射各项目不统一，平台以 `project_env_config.ref` 配置每个「项目+环境」对应的分支。触发动作不变（在该分支上 play 入口 `build_*` 手动 job）。
> ⚠️ 该样本本身 `SERVER_HOST` 写死，说明**目标服务器可能由 runner/部署脚本按分支区分**，平台无需关心服务器细节，只需按"环境→分支→触发"驱动即可。

## 9. 数据模型（平台侧，最小集）

```sql
-- 用户（缓存自 GitLab，平台扩展字段）
user(id, gitlab_user_id, username, name, avatar_url, is_admin, created_at)

-- GitLab token（加密存储）
oauth_token(id, user_id, access_token_enc, refresh_token_enc, expires_at)

-- 项目缓存（定时/手动同步）
project_cache(id, gitlab_project_id, name, path_with_namespace, group_id,
              default_branch, last_synced_at)

-- 分组缓存
group_cache(id, gitlab_group_id, name, full_path, parent_id)

-- 环境字典
environment(id, code, name, sort, color, default_min_access_level)

-- 项目-环境-分支-触发映射（ref = 该环境绑定的分支，按分支区分环境）
project_env_config(id, gitlab_project_id, env_code, ref, strategy,
                   job_name_pattern, extra_variables_json, min_access_level)
-- 唯一约束: (gitlab_project_id, env_code)；ref 即环境绑定分支，如 测试→develop

-- 部署记录（核心业务实体）
deployment(id, gitlab_project_id, project_name, ref, env_code, strategy,
           gitlab_pipeline_id, gitlab_job_id, status, triggered_by_user_id,
           triggered_by_name, variables_json, note, started_at, finished_at,
           duration_sec, fail_reason)

-- 收藏
favorite(id, user_id, gitlab_project_id, created_at)

-- 审计日志
audit_log(id, user_id, action, target_type, target_id, detail_json, ip, created_at)
```

`deployment.status`：`pending | running | success | failed | canceled`。

## 10. 平台 API 契约（前后端对接）

> 前缀 `/api`，认证：JWT（Header `Authorization: Bearer`）。响应统一 `{ code, message, data }`。

### 认证
- `GET /api/auth/login` → 302 GitLab 授权
- `GET /api/auth/callback?code&state` → 建会话，返回/重定向带 JWT
- `GET /api/auth/me` → 当前用户信息
- `POST /api/auth/logout`

### 项目与分组
- `GET /api/groups/tree` → 分组树（当前用户可见）
- `GET /api/projects?groupId&keyword&page&pageSize&onlyFavorite` → 项目列表（已含权限过滤、最近部署信息）
- `GET /api/projects/:id/branches?keyword` → 分支列表
- `GET /api/projects/:id/tags` → tag 列表
- `GET /api/projects/:id/environments` → 该项目可部署环境列表，每项含 `{ envCode, name, ref(绑定分支), deployable(当前用户是否可部署) }`
- `POST /api/projects/:id/favorite` / `DELETE /api/projects/:id/favorite`

### 部署
- `POST /api/deployments` → 触发部署
  body: `{ projectId, env, ref?, variables?, note? }`（`ref` 默认由 env 绑定分支带出，省略即用 `project_env_config.ref`；显式传入视为高级改分支，后端校验权限+二次确认标记）
  返回: `{ deploymentId, pipelineId, jobId? }`（后端做权限校验 + 并发锁 + 落库）
- `GET /api/deployments/:id` → 部署详情（含实时状态聚合）
- `GET /api/deployments/:id/logs?offset` → 增量日志（或 SSE：`GET /api/deployments/:id/stream`）
- `POST /api/deployments/:id/cancel` → 取消
- `GET /api/deployments?projectId&env&status&from&to&triggeredBy&page&pageSize` → 历史列表

### 管理（管理员）
- `GET/PUT /api/admin/environments`
- `GET/PUT /api/admin/projects/:id/env-config`
- `POST /api/admin/sync` → 触发项目/分组同步
- `GET /api/admin/audit-logs?...`
- `GET/PUT /api/admin/admins`

```

- 终态（success/failed/canceled）后停止轮询，落库 finished_at/duration。

## 14. 风险与待确认事项

| 项 | 说明 | 处理 |
| --- | --- | --- |
| 触发机制不统一 | 各项目 `.gitlab-ci.yml` 的部署 job 命名/方式可能不一致 | **开发前抽查样本，固化命名规范与映射规则（§8.4）** |
| GitLab OAuth Application | 需管理员在 GitLab 创建应用、配回调与 scope | 提前申请 |
| 权限实时性 | 用户在 GitLab 权限变更后缓存延迟 | access_level 缓存 TTL 短 + 部署前实时校验 |
| 日志量大 | 大型部署日志拉取压力 | 增量字节 range 拉取 + 前端虚拟滚动 |
| Token 安全 | 泄露风险 | 加密存储、最小 scope、定期轮换、不入日志 |
| GitLab 版本差异 | 不同版本 API 字段差异 | 确认 GitLab 版本，锁定 API v4 行为 |
