# 项目代码问答：全文阅读 + 长期记忆 + 会话历史 — 开发文档

> 版本：v1　｜　日期：2026-06-18　｜　范围：Deploy Center「项目列表 · 代码问答」功能重构

---

## 1. 背景与问题

项目列表里每个项目可打开「代码问答」抽屉，对该仓库代码做 AI 问答。重构前存在三个问题：

1. **读得太少 / 读不全。** 用户反馈「每次只能阅读 5 个文件」。实际排查发现那个 `5` 是并发抓取批大小 `CHUNK = 5`（`projects.service.ts`），并非真实上限；真实上限是一套「一次性注入」逻辑：
   - 先让模型从目录清单里「点名」最多 `MAX_SELECT_FILES = 30` 个文件，失败回退启发式 `MAX_PICKED_FILES = 24` 个；
   - 抓原文塞进 system prompt（单文件截断 28K、总预算 200K 字符），**一次性**发给模型。
   - 根本缺陷：模型不能「边读边查」，第一轮挑漏了文件就答不全、也无法补读。
2. **没有记忆。** 模型每次都从零理解仓库，问过的结论不会沉淀。
3. **没有会话历史。** 对话只存在前端组件 state，抽屉 `destroyOnClose`，**一关即丢**，后端无任何存储。

## 2. 需求

- 去掉「只读少量文件」的限制，做到**按需全文阅读**（要读多少读多少）。
- **记忆功能**：跨会话记住项目要点，越聊越懂。
- **会话历史**：对话落盘、可列出、可续聊。

## 3. 方案选型

### 3.1 全文阅读：从「一次性注入」改为「Agent 工具循环」

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. Agent 工具循环（**选用**） | 给模型 `list_repo_files` / `read_file` / `grep` 工具，模型自己迭代浏览、检索、读全文，直到能回答 | 真正不限文件数、可读全文；依赖网关支持 Anthropic `tool_use` |
| B. 放大预算 + 多轮点名 | 不依赖 tool_use，加大文件数/字符预算 + 多一轮补读 | 改动小，但仍受单次上下文窗口约束，超大仓库读不全 |
| C. RAG / 向量检索 | 仓库切块入向量库，按问题召回 | 需要额外索引基础设施，超出当前内部工具体量 |

**关键约束**：上限不再是「文件个数」，而是「**最大迭代轮数 + 单次工具结果字符上限**」。模型可在轮数预算内任意多读，逼近全文阅读。

### 3.2 网关能力实测（决定能否走 A）

内网 MaaS 网关走 Anthropic 协议（`/anthropic/v1/messages`），但 DeepSeek/GLM/Kimi/Qwen 等模型对 `tools` 的支持不一定一致，因此**先实测**（脚本见 `server/scripts/probe-tooluse.mjs`、`probe-loop.mjs`）：

| 模型 | tool_use 单轮 | 完整循环收敛 |
|---|---|---|
| deepseek-v4-pro | ✅ | ✅ 9 轮 / 20 次调用 |
| glm-5.2 | ✅ | ✅ 4 轮 / 3 次调用 |
| kimi-k2.6 | ✅（id 形如 `functions.read_file:0`） | ✅ 4 轮 / 9 次调用 |
| qwen3.7-max | ✅ | —（未单独跑循环） |
| claude-haiku-4-5 | ✅ | — |
| **qwen3.7-plus** | ❌ HTTP 400 `unknown model` | — |

**结论**：有效模型全支持 tool_use → 确定走方案 A。

**附带发现的 Bug**：`qwen3.7-plus` 是网关不认识的模型 id，用户在界面选「通义千问 3.7 Plus」会直接 400 —— 已从 `AI_MODELS` 白名单移除。

> 多模型 `tool_use` 的 `id` 格式不一致（kimi 用 `functions.read_file:0`，其它用 `call_*`/`toolu_*`）。循环回灌 `tool_result.tool_use_id` 时**按响应里的 `id` 原样回传**，不做任何格式假设，已规避兼容问题。

### 3.3 记忆 & 会话历史存储

沿用现有 `StoreService`（内存 `Map` + JSON 文件防抖落盘，单实例内部工具够用），不引入数据库。新增两类数据：会话 `Conversation`、项目记忆 `ProjectMemory`，均**按「用户 + 项目」私有**。

## 4. 架构与数据流

```
前端 ProjectChatDrawer
  ├─ 左侧：会话列表（GET /projects/:id/conversations）
  │        新对话 / 点击续聊（GET /conversations/:cid）/ 重命名 / 删除
  └─ 右侧：对话区 → POST /projects/:id/chat { conversationId?, question, model, ref }
                                │
                                ▼
ProjectsService.chat()
  1. 解析/校验会话归属，确定分支 ref
  2. 拉取文件树（一次），过滤忽略路径
  3. 注入「项目长期记忆」到 system
  4. AiService.chatAgent() ── 工具循环 ──┐
        ↑ tool_result 回灌               │ tool_use
        └── onTool: list_repo_files / read_file / grep
                     （走 GitlabService，带请求内文件缓存）
  5. 落盘会话（user/assistant 两条 message）
  6. 异步增量更新项目记忆（best-effort，不阻塞返回）
  7. 返回 { conversationId, title, answer, usedFiles, ref }
```

## 4.5 工作原理详解（重点）

### 4.5.1 AI 是怎么读当前仓库代码的

不是把代码一次性塞给模型，而是**给模型三件工具，让它像人一样自己边搜边读**，循环进行：

1. 后端先调 GitLab `repository/tree` 拉到**当前分支的完整文件树**（最多 2000 个路径，过滤掉 node_modules/dist/二进制/锁文件），并在 system 提示里给出前 400 个作目录预览。
2. 把这份「工具说明 + 目录预览 + 项目记忆 + 用户问题」发给模型。模型自己决定下一步动作，返回 `tool_use`（工具调用）：
   - `grep(query)`：在仓库文件内容里搜关键词 → 返回 `文件:行号: 行内容`，用于**定位**；
   - `list_repo_files(glob?)`：列/筛选文件路径 → 用于**浏览**；
   - `read_file(path)`：读某文件全文（≤5 万字符）→ 用于**精读**。
3. 后端执行该工具（真正去打 GitLab 取数据），把结果作为 `tool_result` 回灌给模型。
4. 模型拿到结果后继续：可能再搜、再读，也可能已经够了就**给出最终文字答案**（`stop_reason` 不再是 `tool_use`）。
5. 这个「调用工具→回灌结果」的循环最多跑 **24 轮**（每轮可并发读多个文件）。轮数是唯一硬上限——所以是"按需读够为止"，而非固定文件数。

> 期间用一个**请求内文件缓存**：同一次问答里 `read_file`/`grep` 命中同一文件只打一次 GitLab。
> 真实实测：问"这是什么框架"，glm 读 3 个文件就收敛，deepseek 读了 20 个，模型自行决定读多少。

### 4.5.2 会话是怎么保存的

「会话」= 一问一答的完整记录，按 **用户 + 项目** 私有，存在后端 `StoreService`（内存 `Map` + JSON 文件落盘，进程重启不丢）。

- **首次提问**：前端不带 `conversationId`。后端答完后 `createConversation()` 新建一条会话，用首个问题生成标题（`deriveTitle`，截断 24 字），把 user/assistant 两条消息（assistant 还带 `usedFiles`）写进去，返回新的 `conversationId` 给前端。
- **续聊**：前端带上 `conversationId` + 当前问题（**只发当前这句，不发整段历史**）。后端从落盘记录里取出该会话最近 `CHAT_HISTORY_TURNS = 12` 轮作为上下文，答完把新一问一答追加进去（`updateConversation`，刷新 `updatedAt`）。
- **历史以服务端为准**：前端不再保存对话；关掉抽屉数据不丢，重开从 `GET /projects/:id/conversations` 拉列表，点某条走 `GET /conversations/:cid` 还原完整消息 + 当时的分支/模型。
- 列表接口**不返回消息体**（只返标题/分支/时间），省流量；详情接口才带全量消息。重命名/删除走 `PATCH`/`DELETE`，均校验 `userId` 归属，防越权。

### 4.5.3 记忆是怎么做的

记忆 = 一份关于**这个项目**的「长期要点摘要」，同样按 **用户 + 项目** 私有，独立于具体会话。

- **怎么生成**：每轮问答**回答返回之后**，后端异步（不阻塞用户）把「已有记忆 + 最近这一问一答」再发一次给模型，让它**重写出一份更新后的精炼要点**（技术栈、目录与模块职责、入口与启动、关键实现位置、部署方式等，纯文本 ≤4000 字），存进 `projectMemory[userId:projectId]`。
- **怎么用**：每次**新提问**时，后端把这份记忆塞进 system 提示（"关于本项目你已积累的记忆…，但以本次实际读到的代码为准"）。于是模型开聊前就已经"认识"这个项目，不必每次从零摸索——**越聊越懂**。
- **best-effort**：记忆更新失败只告警，不影响用户拿到答案；它是背景增强，不是必经路径。

> 三者关系：**会话**是逐字的对话流水；**记忆**是从多次会话里提炼的、跨会话复用的项目认知；**读代码**是每次回答时即时去仓库取真实依据。回答既参考"记忆"（快速进入状态），又以"即时读到的代码"为准（保证不臆造）。

## 5. 后端实现

### 5.1 类型（`server/src/common/types.ts`）

- `ChatMessageStored`：落盘的单条消息（`role` / `content` / `usedFiles?` / `ts`）。
- `Conversation`：会话，绑定 `userId + gitlabProjectId`，含 `title` / `ref` / `model` / `messages[]` / 时间戳。
- `ProjectMemory`：项目长期记忆，键 `userId + gitlabProjectId`，含自然语言 `summary`。

### 5.2 存储（`server/src/core/store.service.ts`）

新增两个 `Map` 并接入 `load()` / `persist()` 快照：

- `conversations: Map<convId, Conversation>`
- `projectMemory: Map<"${userId}:${projectId}", ProjectMemory>`

新增方法：`createConversation` / `getConversation` / `listConversations`（不含消息体，按更新时间倒序）/ `updateConversation` / `deleteConversation` / `getProjectMemory` / `setProjectMemory`。

### 5.3 AI 工具循环（`server/src/prompts/ai.service.ts`）

新增 `chatAgent(apiKey, { system, messages, tools, model, maxIterations, onTool })`：

- 循环：POST `messages` → 取 `content` 块 → **原样回灌**为 assistant 消息（含 `thinking` / `tool_use`，保证签名与多模型兼容）。
- `stop_reason !== 'tool_use'` → 收集 `text` 块返回最终答案。
- 否则对每个 `tool_use` 调 `onTool`，结果包成 `{ type:'tool_result', tool_use_id, content }`（单条截断 `TOOL_RESULT_MAX_CHARS = 60_000`）回灌，继续下一轮。
- 轮数用尽（`maxIterations`，默认 24）仍未收敛：去掉 tools、追加「请基于已读内容直接作答」逼出最终回答，避免空手而归。
- 抽出统一的 `postMessages()` 复用请求逻辑。
- 同时移除失效模型 `qwen3.7-plus`。

### 5.4 问答主流程与工具（`server/src/projects/projects.service.ts`）

`chat()` 重写：

- 入参 `{ conversationId?, question?, messages?, model?, ref? }`（`question` 优先，兼容旧版 `messages`）。
- 分支优先级：本次显式 `ref` > 会话原 `ref` > 仓库默认分支。
- **请求内文件缓存** `fileCache`：`read_file` 与 `grep` 共用，避免重复打 GitLab。
- 三个工具（`REPO_TOOLS` 定义 + `runRepoTool` 执行）：
  - `list_repo_files(glob?)`：从文件树按子串过滤，返回路径清单（上限 `LIST_FILES_LIMIT = 400`）。
  - `read_file(path)`：读全文，容忍 `./` 前缀与仅文件名，超 `READ_FILE_MAX_CHARS = 50_000` 截断并标注。
  - `grep(query, path_glob?)`：全文检索，返回 `路径:行号: 行内容`；扫描上限 `GREP_MAX_FILES = 200`、命中上限 `GREP_MAX_HITS = 80`。
- `usedFiles`：从本轮 `read_file` 调用去重得出，用于前端「读过的文件」展示。
- 落盘会话（新会话自动建并用首个问题生成标题 `deriveTitle`）。
- `updateProjectMemory()`：把「旧记忆 + 最近一轮问答」交给模型重写出精炼要点（≤ `MEMORY_MAX_CHARS = 4_000` 字），异步 best-effort 写入。

会话 CRUD：`listConversations` / `getConversation`（校验归属）/ `renameConversation` / `deleteConversation`。

预算常量（取代旧的固定文件数上限）：

```
AGENT_MAX_ITERATIONS = 24   工具循环最多轮数
AGENT_TREE_PREVIEW   = 400  system 目录预览条数
LIST_FILES_LIMIT     = 400  list_repo_files 返回上限
READ_FILE_MAX_CHARS  = 50_000
GREP_MAX_FILES       = 200
GREP_MAX_HITS        = 80
MEMORY_MAX_CHARS     = 4_000
CHAT_HISTORY_TURNS   = 12    续聊带入的最近轮数
```

### 5.5 接口（`server/src/projects/projects.controller.ts`）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/projects/:id/chat` | 问答（带 `conversationId` 续聊），返回 `{ conversationId, title, answer, usedFiles, ref }` |
| GET | `/projects/:id/conversations` | 我在该项目下的会话列表（不含消息体） |
| GET | `/conversations/:cid` | 会话详情（含完整消息，用于续聊还原） |
| PATCH | `/conversations/:cid` | 重命名 |
| DELETE | `/conversations/:cid` | 删除 |

## 7. 关键决策与权衡

- **上限按「轮数」而非「文件数」**：这是「全文阅读」的核心。轮数预算（24）足够读几十个文件 + 多次检索，又能兜底防止无限循环。
- **assistant 内容块原样回灌**：不裁剪 `thinking`/签名，保证跨模型（尤其 kimi 的 thinking + 自定义 tool_use id）兼容。这是多轮协议最易错的点，已用真网关验证收敛。
- **历史以服务端为准**：前端只发当前问题，避免「前端篡改历史」和重复传输；续聊从落盘记录还原。
- **记忆异步更新**：放在回答返回之后 best-effort 执行，失败仅告警，不影响用户拿到答案。
- **请求内文件缓存**：同一次问答里 `read_file`/`grep` 多次命中同一文件只打一次 GitLab。

## 10. 后续可优化

- 同一轮内多个 `tool_use` 目前**顺序**执行 GitLab 读取，可改并发加速（注意 GitLab 限流）。
- `grep` 是线性扫描原文，超大仓库可考虑接 GitLab 搜索 API 或预建索引。
